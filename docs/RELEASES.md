# Signing and releases

[简体中文](RELEASES.zh-CN.md)

Release titles are the tag itself: `v<major>.<minor>.<patch>-r<revision>`, with a lowercase `r`. Write concise English release notes in `docs/releases/<tag>.md`, with a Simplified Chinese counterpart named `<tag>.zh-CN.md`. The GitHub description uses the English notes and links to the Chinese document.

## Software packages

Upload exactly three packages:

- `armhpc-ota-<version>-windows-x64.msi`
- `armhpc-ota-<version>-linux-cli.tar.gz`
- `armhpc-ota-<version>-maintenance.tar.xz`

Include licenses, dependency records, instructions, and corresponding source information inside the packages. Keep build records and checksums locally. GitHub's automatic Source code links are generated by the platform.

`tools/build-msi.py` builds the Windows installer; `tools/build-linux-cli.py` builds the Linux x86_64/ARM64 controller. `tools/package-runtime.py` prepares the device runtime, and `python -m armhpc_ota.lan_publish tools --help` describes maintenance signing.

Build the Linux controller from a clean committed checkout. `--source-ref` must
resolve to that checkout's HEAD; check out an older ref before building it. The
builder exports the resolved commit once, publishes both architectures from that
snapshot, and includes the same source archive in the package. `BUILD-INFO.json`
records the commit and source archive SHA256. Pending tracked or untracked source
changes are rejected before publishing.

```sh
python tools/release-policy.py --tag v1.0.0 --directory /path/to/packages
python tools/release-policy.py --tag v1.0.0 --directory /path/to/packages --apply
```

The policy previews changes by default. It verifies all three uploads before removing extra attachments and uses the matching English release document unless `--notes` is supplied. Existing packages with different bytes are rejected; use a new version rather than overwrite a published package.

## Device maintenance

Maintenance contains `manifest.json` and `runtime.tar.xz`. Devices verify the signature against their existing Ed25519 trust store and check payload hashes, version, board, architecture, layout, roles, and destinations. A key carried inside a package does not become trusted automatically.

SSH/SFTP and USB serial use the same persistent maintenance task. An operation started in the normal system first enters Rescue, then updates the normal system and the writable layers for Rescue A/B. Resume interrupted tasks with their original IDs and package bindings; backups support rollback.

Software versions, system release IDs, manifest sequences, boot ABI, Guardian protocol, and JSON `protocol: 1` are managed independently. Software maintenance does not rewrite signed system manifests or existing payloads. Keep keys, credentials, device backups, and firmware binaries outside source archives.


## Release numbering

Use `vA.B.C-rN`, with a lowercase `r` and a positive revision number. For each repository independently, advance the base version by one patch, one minor with patch reset to zero, or one major with minor and patch reset to zero. Examples: `1.2.3` to `1.2.4`, `1.3.0`, or `2.0.0`. Within the same base version, revisions increase but need not be consecutive: `r1`, `r3`, and `r9` may be published directly. Previously published numeric-only tags remain supported.

The release title equals its tag. Artifact filenames include the revision. Compatibility comparisons continue to use the numeric base version, explicit capabilities and the signed manifest requirements. Firmware signature sequences still increase independently. Publication checks the repository's published release history before any upload or metadata change. Existing versioned assets remain immutable.
